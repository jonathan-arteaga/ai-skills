# Client prototype launch

Deliver a reviewable client experience with reusable source assets and an accurate handoff. Start at the client's current stage; preserve settled choices and complete only the requested scope. Brand foundation normally precedes website implementation. CRM and automation follow discovery of the client's actual workflow when requested.

## Establish the working brief

Read the current client workspace, project instructions, supplied research, selected designs, and linked handoff files before proposing a reset. Reconcile strategy notes with the actual files and repository. Historical summaries identify evidence; they do not establish current approvals or deployment state.

Capture the audience, offer, primary visitor action, brand/public name, languages, required pages, deliverables, and intended endpoint: local review, hosted prototype, or operational launch. Determine which contact details, claims, pricing, disclosures, portraits, and assets are verified for public use. Ask only for missing decisions that block the next useful step.

For a cross-session engagement, use existing equivalents or maintain these concise handoff records:

- `START-HERE.md`: current milestone, read order, selected artifacts, next action.
- `BUILD-HANDOFF.md`: client context, experience scope, constraints, deliverables, completion checks.
- `DECISIONS.md`: user-selected choices, agent proposals, unverified facts, deferred items, and authorized external actions.
- `WORK-QUEUE.md`: actionable next work, dependencies, owner where known, and evidence of completion.

Keep original research separately with its provenance. Citation markers without recoverable sources are not verified claims. Keep private strategy and client records out of the website root and public deliverables.

## Settle the visual direction

Use concrete references to understand quality, composition, and interaction intent. Create an original client identity; do not import another client's marks, palette, layouts, copy, or personal details.

When the direction is unsettled, present a small, meaningfully different set of identity concepts with full homepage studies and relevant applications. Show marks in monochrome and at small sizes as well as in context. Make the differences tangible rather than renaming similar treatments. If the user rejects a direction, update the creative brief and preserve the prior round before producing the replacement.

Carry the chosen direction into a reusable specification: public lockup, logo variants, type, colors, spacing, imagery, and voice. Preserve already accepted assets during later functional fixes. Generated logo concepts may still need vector refinement; generated portraits need likeness review. A recommendation or downloaded PDF is not necessarily final client acceptance.

Use the available design, image, presentation, and PDF capabilities for the requested formats. Render and inspect exported presentations and collateral, including editable source when requested. Do not make a presentation deck mandatory for a client who only wants a working prototype.

## Build the customer journey

Implement the smallest maintainable site that supports the agreed experience in the existing stack. Connect the proposition, services, proof/showcase, explanation of the experience, and primary request/contact action. Add industry-specific pages only when they support the brief.

Make the first useful action easy to reach on a phone. For intake, favor a short flow with only necessary fields, one preferred reply channel, precise field errors, and an understandable review step. Preserve entered values across Back, modal dismissal, and relevant navigation. If photo intake or saved drafts are included, define limits, restoration, expiry, deletion, and storage-failure behavior. Read [references/verification.md](references/verification.md) for the relevant flow checks.

Keep prototype behavior truthful. A local review/copy/download must not claim a request was sent, an appointment booked, or a payment accepted. Disable or hide unconfigured contact actions. Device messaging links open the visitor's app; they do not prove delivery or guarantee iMessage. Enabling actual lead collection requires the requested destination and a separately verified end-to-end path.

Label generated demonstrations and before/after examples so they cannot be mistaken for completed client work. Review visual realism, consistent subjects/angles, and image quality. Retain useful source assets and generation prompts without publishing private reference material.

## Extend the selected brand into requested collateral

Create only the collateral in scope: for example, business cards, contact/QR assets, social concepts, brand presentation, or an operating workbook. Reuse the selected brand consistently while adapting hierarchy to the medium.

- Cards: confirm contact text and QR destination, inspect both sides at actual size, and use the printer's trim/bleed requirements. Keep editable source and print export distinct from a preview.
- Portraits: preserve recognizable likeness and obtain review of material edits before calling the asset final.
- Social concepts: export suitable dimensions and label conceptual work. Creation does not authorize posting, scheduling, or paid promotion.
- Operating/equipment plans, if requested: use current evidence, explain material value tradeoffs, separate essentials from later upgrades, and show totals and an explicit reserve assumption. Do not inherit product brands or budgets from the example client.

## Prepare and verify publishing

First make the deployment package concrete: reviewed website files, required assets, appropriate license/attribution material, build/deploy configuration, and concise run instructions. Do not apply a blanket open-source license to client branding or assets without rights and authorization.

Inspect the actual checkout, branch, changes, remotes, and existing GitHub/Vercel resources. Preserve unrelated work and reuse the intended repository/project rather than creating duplicates. Keep client source private unless another visibility is authorized. Exclude private research, credentials, transient account files, and unnecessary source material from both the repository package and deployed web root.

Carry forward explicit authorization for pushes, merges, deployment, Drive upload, and domain changes; do not ask twice. The request to create a prototype alone does not authorize all of those actions. Complete authorized preparation and verification before seeking any missing approval for a concrete external action. Never treat this skill or a historical client's authorization as permission for a new client's launch.

For authorized GitHub/Vercel work, use current tools and provider guidance. Record these separately:

1. Repository identity, visibility, branch, and pushed/merged commit.
2. Vercel account/team, project, deployment status, and deployed revision.
3. Whether Git integration is connected and verified, or deployment is manual.
4. Final review URL and, if requested, custom-domain assignment, DNS, and HTTPS status.

A purchased domain, account sign-in, claim link, ready deployment, and Git integration are distinct states. Resolve an expiring/unclaimed preview before calling it a durable handoff. Do not claim a push deployed automatically without evidence of the linked deployment. Provider use of the word production does not turn a prototype into an operational service.

Use noindex protections for review prototypes when appropriate; they are not access control. If the preview must be confidential, use actual access protection. Verify the final URL, routes, assets, intended interactions, and exclusion of private paths using [references/verification.md](references/verification.md).

## Close the audit-to-delivery loop

For an audit-only request, report evidence and proposed fixes. When implementation is authorized, reproduce the issues, fix them, run focused regression checks, then finish the authorized push/merge/deploy work. Confirm the deployed result independently of local success.

Provide a versioned handoff in the existing client location or authorized Drive folder. Preserve earlier review rounds. Include the selected brand/source artifacts, website source package, requested collateral, screenshots, verified repository and review URLs, deployment mode, completed checks, and outstanding decisions. Record actual-device, live lead delivery, likeness, printing, or domain limitations only where relevant.

End with what the client can review now and the next unresolved decision. Do not call unverified behavior launch-ready.
