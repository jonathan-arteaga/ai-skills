# Client website launch

Carry the current client handoff through the requested endpoint: build plan, local prototype, hosted review, or operational launch. Start at the actual stage. Preserve selected branding and existing implementation; do not restart brand exploration because an older handoff says “brand first.”

This skill focuses on website delivery from a handoff. For a broader request to develop an original identity and collateral, the installed `client-prototype-launch` skill can guide that work. It is not a prerequisite for an ordinary website launch.

## Reconcile the handoff before building

Read the client's project instructions and existing equivalents of `START-HERE.md`, `BUILD-HANDOFF.md`, `DECISIONS.md`, and `WORK-QUEUE.md`, then the relevant research and asset register. Locate the actual working project rather than assuming a downloaded package or strategy mirror is current.

Resolve decisions by authority and scope: current explicit user instructions supersede conflicting older proposals; confirmed client facts and approved assets outrank unverified research. Record what changed and which files or concepts are superseded. A supplied brokerage name confirms the supplied affiliation, not every license detail or advertising requirement. A visible attachment does not establish its exact colors; inspect the source image/brand sheet when carrying those values into the site.

Recover answers from supplied research and current files before asking the user again. Keep claim provenance, review status, and allowed public wording clear. Research citation tokens without recoverable sources do not verify awards, reviews, service areas, or legal statements. Use current authoritative sources for claims that require verification; never invent testimonials or broker disclosures.

Summarize build readiness as three groups: settled inputs, draft work that can proceed, and missing inputs with the specific milestone they block. A deferred domain, pending final photo, or unavailable CRM access usually need not block a local prototype. Use truthful draft states and keep unresolved public claims out of release content.

Keep a compact record of client identity, audience, primary visitor action, selected brand version, languages, route scope, contact destination, project location, domain/account ownership, authorized actions, and unresolved decisions. Update the existing handoff files instead of creating competing documentation systems.

## Make the website scope concrete

Inventory each page with its purpose, primary CTA, locale equivalents, source copy/assets, approval state, and dependencies. Count page types separately from public routes; eight page types translated into two languages means sixteen routes, before any separately scoped pages. Confirm the actual scope rather than inheriting a historical client's counts.

When English/Spanish is required, build equivalent visitor journeys in both languages. Localize navigation, footer, forms, errors, confirmations, metadata, image alternatives where relevant, and privacy text as well as body copy. Maintain a shared route map so the language switch opens the equivalent page and navigation stays in the selected language. Use language names such as “English” and “Español.” Agree a deliberate fallback when an equivalent page is unavailable; do not silently send every switch to the homepage.

Keep copy in a maintainable structured source and record Spanish review status. Review for meaning, natural phrasing, and text expansion. Do not label machine translation client-approved. If proof or story permissions are missing, omit the affected content and links consistently in both languages and record the scope change.

Apply selected marks, palette, type, imagery, and voice through reusable assets and design tokens. Show desktop/mobile examples if visual decisions remain unresolved. Final vector cleanup can proceed alongside a prototype when usable approved-direction assets exist. Do not bring back a rejected palette from older homepage concepts.

## Establish a clean client repository

Inspect the working path, Git status, branch, remotes, project instructions, and existing repository before scaffolding. Reuse the intended client project; keep client implementation separate from the consultancy's marketing site and synced strategy sources. Preserve unrelated changes and back up unique material before authorized cleanup.

Keep the repository focused on website code, required assets, technical instructions, and the working handoff. Link to the authoritative strategy/research home instead of building a duplicate planning library or automatic synchronization system. Keep private research, credentials, and unapproved assets out of the deployed web root. Do not combine separate clients in one repository because a prior consultancy project chose “one repo initially.”

Use the existing suitable stack. If none is selected, Next.js/TypeScript with GitHub/Vercel is a provisional option, not a mandate. Verify current provider/framework guidance during setup. Favor structured content and a managed inquiry destination; add a CMS, database, or new CRM only when editing or operational needs justify it.

Centralize client identity, contact details, affiliation/disclosures, locale routes, metadata configuration, and brand tokens. Record actual repository/account ownership and temporary arrangements. Prepare run/build instructions, required environment variable names without values, and a reproducible dependency lockfile.

## Implement and verify inquiry delivery

Build the homepage, shared navigation/footer, remaining scoped pages, and inquiry flow around the agreed visitor action. Use the client's existing suitable destination before adding another system. Keep later CRM replacement, nurture, AI replies, portals, and workflow automation as separate scope unless explicitly requested.

Prototype using synthetic data and clearly described simulated delivery. A review screen, copied message, opened mail app, or success toast is not evidence that a lead arrived. Enable real collection only with a confirmed destination and authorization covering the action. Sending test messages also requires that scope; do not contact a client or broker merely to complete a checklist.

Collect only useful contact and inquiry fields, including preferred language when relevant. Preserve entered values on recoverable errors, validate on the server for a public submission endpoint, and include suitable spam controls. Keep personal data out of URLs, analytics payloads, and routine logs. Inquiry intent does not imply marketing consent.

For a live integration, verify a synthetic inquiry is actually received in the intended destination, carries the right language/source context, and has an identifiable follow-up owner. Exercise validation, rejection, failure, retry, and duplicate-submission behavior. Document limitations honestly if receipt cannot be verified.

## Prepare the release and carry out authorized launch

Use [references/launch-checklist.md](references/launch-checklist.md) during implementation QA and release preparation. Mark each applicable item with evidence and status: verified, pending, blocked, or not applicable with a reason. Avoid declaring the whole launch blocked when an independent deliverable can proceed.

Make the release concrete before requesting any missing approval: working preview, exact repository/revision, proposed domain and provider/account targets, completed checks, remaining launch inputs, costs/ownership, and rollback approach. Carry forward existing explicit authorization without asking twice. A request to build locally, a historical client's permission, or this skill itself does not authorize publishing, changing DNS, creating paid services, or messaging others.

Once authorized, complete the relevant push/merge/deployment/cutover and verify the resulting URL. Track repository publication, deployment, Git integration, domain assignment, DNS/HTTPS, indexing, and inquiry receipt as separate outcomes. A domain promised later stays pending; do not fabricate it or block local work on it. A ready hosting build alone does not prove an operational client website.

For a requested identity or brokerage transition, inventory affected domains, mailboxes, profiles, signatures, QR codes, and contact links with owner, desired verified values, status, and readback evidence. Preserve a working inquiry path during cutover. Track third-party changes outside the client's control without treating a request sent as a completed update.

## Return a durable handoff

Update the current decisions and work queue at each milestone with completed task IDs, artifact/repository/preview locations, revision, checks and results, changes in decisions, outstanding inputs and affected deliverables, and the exact next task. Transfer these updated records between strategy and implementation conversations; do not assume either conversation can see the other's latest messages.

For launch, include a short operating guide covering lead destination, content edits, account ownership, recurring costs, recovery/rollback, and support contact/scope. Report physical-device tests, Spanish approval, live delivery, and domain status only to the extent verified. Do not promise ongoing monitoring or unlimited maintenance without an agreement.
